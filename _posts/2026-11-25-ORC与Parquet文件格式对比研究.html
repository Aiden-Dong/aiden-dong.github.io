ORC 与 Parquet 文件格式对比研究

研究对象：ORC Java 实现(orc-source-code-analyze，1.9.0-SNAPSHOT)、Parquet Java 实现(parquet-java，1.19.0-SNAPSHOT，编码部分和 Paimon 1.0 依赖的 1.13.1 一致)。
第 1 ~ 3 节讲文件格式本身：结构层级、编码、压缩。第 4 节以后是索引、过滤等其他能力和两者的优劣。

一页结论

设计思路
本质相同
都是"按行切大块，块内按列存储，元数据放尾部"。写入时都是先编码(字典、RLE、位打包)，再通用压缩(zstd 等)。
最关键的差异
字符串字典规则
ORC：不同值比例 ≤ 0.8 就用字典，字典不限大小。Parquet：字典页超过 1 MB 就回退到 PLAIN。结果是 ORC 文件更小，但读取时堆里有大块长期存活的字典。
性能
没有绝对的赢家
ORC 的索引更细且各列对齐，高基数字符串存得更省；Parquet 生态更广，字典大小有上限，读取时内存更稳定。哪个更快取决于数据和查询引擎，要用自己的数据实测。

1. 文件结构：按层级看

两种格式都可以拆成同样的几层。下面用颜色表示"同一个概念"，左右两边颜色相同的框作用相同，名字和细节不同。

文件整个文件 行分块按行切的大块 列大块里一列的数据 列内细分一列再拆成的单元 压缩单位一次压缩/解压的数据 编码单位一段编码后的数据 索引统计和定位信息 元数据描述文件内容

1.2 磁盘上的实际顺序

层级树是逻辑关系，下面是字节在文件里从左到右的排列。以 3 列(a 是 int，b、c 是字符串)为例。

ORC 一个 stripe：先放所有列的索引，再放所有列的数据，最后是 stripe footer。

a ROW_INDEXb ROW_INDEXc ROW_INDEXc BLOOM a PRESENTa DATA b DATA(下标)b LENGTHb DICTIONARY_DATA c DATA(字节)c LENGTH Stripe Footer
b 用字典编码(DICTIONARY_V2)，c 不同值太多，用直接编码(DIRECT_V2)。每个色块内部再按 256 KB 切成压缩块。

Parquet 一个 row group：一列的所有 page 连续存放，然后是下一列。

头a page 1头a page 2 头b 字典页头b page 1头b page 2 头c 字典页头c page 1(字典)头c page 2(PLAIN)
"头"是不压缩的 Page Header。c 的字典超过 1 MB 后，后面的 page 回退成 PLAIN，同一个 column chunk 里两种编码并存。row group 里没有索引，索引统一放在文件末尾。

PAR1RG 1RG 2… 索引/BloomFooter长度+PAR1

"按用途拆"和"按行拆"的后果 ORC 的 stream 覆盖整个 stripe，压缩块的边界和行无关。所以 ORC 的行索引要记三层位置：哪个压缩块、解压后块内的偏移、RLE 段内第几个值，才能从某个 1 万行开始解码。
Parquet 的 page 本身就是一段行，跳过一个 page 就是跳过一段行，Offset Index 只需要记 page 的文件偏移。代价是每列的 page 边界不同，多列过滤时要对各列命中的行范围求交集。

1.4 读取路径：从文件末尾到值

ORC

① 读最后 1 字节得到 PostScript 长度
→
② 读 PostScript知道压缩方式和 Footer 长度
→
③ 读 Footer / Metadataschema、stripe 列表和统计，跳过不需要的 stripe
→
④ 读 Stripe Footer 和 ROW_INDEX选出要读的 1 万行组
→
⑤ 读需要的 stream按 256 KB 块解压，再解码 RLE v2 / 字典

Parquet

① 读最后 8 字节Footer 长度 + 魔数
→
② 读 Footerschema、row group 列表和 column chunk 统计，跳过不需要的 row group
→
③ 读 Column / Offset Index算出每列命中的行范围，求交集
→
④ 读命中的 page先读 Page Header，再读 page 体
→
⑤ 解压整个 page 体再解码级别和值

2. 数据编码

编码是格式自己做的第一层压缩。它知道每列的类型，利用"这一列的数据长什么样"减少字节数，比如值重复、取值范围小、单调递增。编码之后的字节流再交给 zstd 这类通用压缩(第 3 节)。读取时顺序相反：先解压，再解码。

写入：列值 ──▶ 编码(字典 / RLE / 位打包 / 增量) ──▶ 通用压缩(zstd / snappy / lz4) ──▶ 磁盘 读取：磁盘 ──▶ 解压 ──▶ 解码 ──▶ 列向量 ──▶ 计算引擎

本节先用一张表汇总每种数据类型在两种格式里用什么编码(2.1)，再逐个讲每种编码的具体实现(2.2)，最后用 GIO 的两类列做对比(2.3、2.4)。

2.2 编码详解

(1) PLAIN / 原样存储

类型Parquet PLAINORC 对应的原样部分
INT32 / INT644 / 8 字节，小端序。100 → 64 00 00 00不用原样存储，整数一律用 RLE v2
FLOAT / DOUBLE4 / 8 字节 IEEE 754，小端序DATA stream 原样 IEEE 754
字符串 / BINARY每个值：4 字节长度(小端) + 内容。"abc" → 03 00 00 00 61 62 63。36 位的 sessionid 占 40 字节DIRECT_V2：内容拼在 DATA stream，长度单独放进 LENGTH stream 做 RLE v2。长度相近时，长度 stream 几乎不占空间
BOOLEAN每个值 1 位，8 个一字节见字节 RLE

同样是"原样存字符串"，ORC 把长度和内容分到两个 stream，长度可以再压缩；Parquet v1 的 PLAIN 把长度夹在每个值前面，每个值固定多 4 字节。

(2) 字典编码

原始值： user_a user_b user_a user_c user_a user_b 字典： [user_a, user_b, user_c] 下标： 0 1 0 2 0 1 ← 下标用整数编码存储

原理两边一样，差别在什么时候用、字典存在哪、多大：

ParquetORC(只用于字符串)
字典存在哪每个 column chunk 开头的 Dictionary Page，字典项用 PLAIN 存每个 stripe 的 DICTIONARY_DATA(字节拼接) + LENGTH(每项长度)
下标怎么存数据页里：1 字节位宽 + RLE / 位打包混合编码。位宽 = ⌈log₂(字典项数)⌉DATA stream，RLE v2
字典顺序按出现顺序追加排好序(默认 orc.dictionary.implementation=rbtree)
用不用先用，不合适再放弃：
  • 字典超过 parquet.dictionary.page.size(默认 1 MB)或条目数超限，后面的值改用 PLAIN
  • 写完第一个 page 时，如果"下标大小 + 字典大小 ≥ 原始大小"，也放弃
  • 已经写出的 page 不变，所以一个 column chunk 里可能两种编码并存
  • 每个 row group 重新试一次
DictionaryValuesWriter.shouldFallBack / isCompressionSatisfying，FallbackValuesWriter		 先统计，再决定：
  • 不同值个数 ÷ 非空行数 ≤ orc.dictionary.key.threshold(默认 0.8)就用字典
  • 在写完第一个 1 万行时判断(orc.dictionary.early.check 默认开启)；stripe 不到 1 万行就在 stripe 结束时判断
  • 一个文件每列只判断一次：doneDictionaryCheck 置为 true 后不再重置，后面的 stripe 沿用结果。数据排过序时，前 1 万行不一定有代表性
  • 字典没有大小上限，每个 stripe 写出并清空一次
StringBaseTreeWriter.checkDictionaryEncoding，OrcConf.DICTIONARY_KEY_SIZE_THRESHOLD
读取时Paimon 用 ParquetDictionary.decodeToBinary 按下标逐个取值整个字典读进一个 byte[]，批次里的字符串直接引用它(setRef)，不拷贝。这个数组要活到 stripe 处理完

(3) RLE / 位打包混合编码(Parquet)

Parquet 里几乎所有整数序列都用它：定义级别、重复级别、字典下标、v2 的布尔值。数据被切成若干段，每段开头是一个变长整数(varint)头，最低位区分两种段：

段类型头内容适合
RLE 段重复次数 << 1(最低位 0)一个值，占 ⌈位宽 / 8⌉ 字节同一个值连续出现
位打包段(组数 << 1) | 1(最低位 1)每 8 个值一组，每个值只占"位宽"那么多位，从低位开始紧凑排列值不重复但范围小

例 1：RLE 段。排好序的字典下标：0 重复 7000 次，然后 1 重复 13000 次，位宽 1。

位宽 01varint(7000<<1) 2 字节00varint(13000<<1) 3 字节01

2 万个值只用 8 个字节。RLE 段的长度没有上限，所以排序后的列在 Parquet 里非常省空间。

例 2：位打包段(Parquet 规范里的例子)。值 0 ~ 7，位宽 3，正好一组：

头 0388C6FA

8 个值占 3 个字节。二进制是 10001000 11000110 11111010，从每个字节的低位开始依次放 000、001、010 …

(4) zigzag + RLE v2(ORC)

zigzag：有符号整数先做 (n << 1) ^ (n >> 63)，0, -1, 1, -2, 2 → 0, 1, 2, 3, 4。绝对值小的负数也变成小的正数，后面按位宽打包时不会因为符号位浪费空间。字典下标、长度这类无符号的 stream 不做这一步。

RLE v2：每段最多 512 个值，写入时逐段观察数据，从 4 种子编码里自动选一种(RunLengthIntegerWriterV2，MAX_SCOPE = 512)。每段头的最高 2 位表示子编码类型。下面的字节例子都来自 ORC 规范，都是无符号整数。

子编码什么时候用例子
SHORT_REPEAT同一个值重复 3 ~ 10 次 [10000 × 5]
0A2710
1 字节头(类型、值占几个字节、重复次数) + 值 10000 的 2 字节
DIRECT没有规律 [23713, 43806, 57005, 48879]
5E035CA1AB1EDEADBEEF

2 字节头 + 起始值 2 + 第一个差值 1(zigzag 后是 2) + 后面 8 个差值(2,2,4,2,4,2,4,6)每个 4 位。差值全部相同时，只要头 + 起始值 + 差值，没有后面的打包部分
PATCHED_BASE大部分值集中在一个小范围，个别值特别大 [2030, 2000, 2020, 1000000, 2040, …]：减去基准值 2000 后，大部分值 6 位就够，1000000 这个离群值的高位单独存进"补丁表"。不然整段都要按 20 位存

和 Parquet 的 RLE / 位打包混合比：RLE v2 对整数的分布适应性更强，递增、离群值都有专门处理；但每段最多 512 个值，很长的重复要拆成很多段，每段约 4 字节。Parquet 的 RLE 段长度不限，但只认"完全相同"和"范围小"两种情况。

(5) 字节 RLE(ORC)

  • 格式：控制字节为 0 ~ 127 时，表示后面 1 个字节重复(控制字节 + 3)次，即 3 ~ 130 次；控制字节为 -1 ~ -128 时，表示后面跟着 1 ~ 128 个原样字节。
  • tinyint：值本身就是一个字节，直接做字节 RLE。
  • 布尔和 PRESENT：每 8 个值拼成 1 个字节(高位在前)，再做字节 RLE。全是 true 的 1 万行，就是几个"重复 130 次的 0xFF"。

(6) 空值的表示

Parquet：定义级别ORC：PRESENT stream
存什么每个值一个数字，表示嵌套路径上有几层非空。扁平的可空列最大是 1：1 有值，0 为空每行 1 位：1 有值，0 为空
编码RLE / 位打包混合，v1 page 里前面带 4 字节长度位图 + 字节 RLE
放在哪和值放在同一个 page 体里，先级别后值单独的 stream
没有空值时一个很长的 RLE 段，几个字节整个 stream 省略
值区两者都只存非空的值

嵌套类型(LIST、MAP)在 Parquet 里还要加一组重复级别，表示"这个值是新的一行，还是同一个列表里的下一个元素"，同样用 RLE / 位打包混合编码。ORC 用 LENGTH stream 记录每行的元素个数。

(7) 增量编码和 BYTE_STREAM_SPLIT(Parquet v2)

编码原理适合
DELTA_BINARY_PACKED存相邻值的差。每 128 个值一个块，块内先减去最小差值，再按位宽打包整数、时间戳、自增 ID
DELTA_LENGTH_BYTE_ARRAY所有长度用上面的增量编码，内容拼在一起字符串
DELTA_BYTE_ARRAY每个值存"和前一个值相同的前缀长度 + 剩下的后缀"，前缀长度和后缀长度都用增量编码排好序、前缀相同的字符串
BYTE_STREAM_SPLIT把所有值的第 1 个字节放一起、第 2 个字节放一起……让通用压缩更容易找到规律。默认不开启浮点数
Paimon 1.0 的默认值 writer 版本 v1(ParquetProperties.DEFAULT_WRITER_VERSION = PARQUET_1_0)，这一节的编码都没用上。可以通过 parquet.writer.version=v2 打开，但要先确认 Paimon 1.0 的向量化读取支持这些编码。

(8) ORC 的时间和小数

  • timestamp：拆成两个 stream。DATA 存相对 2015-01-01 的秒数，用有符号 RLE v2；SECONDARY 存纳秒，用无符号 RLE v2，纳秒末尾的 0 会先去掉，再用低 3 位记录去掉了几个，所以毫秒精度的时间戳纳秒部分很小。
  • decimal：DATA 存去掉小数点后的整数，用变长整数(每字节 7 位有效，最高位表示后面还有没有)；SECONDARY 存每个值的小数位数(scale)，用 RLE v2。
  • date：就是天数，一个普通的有符号整数 stream。

3. 通用压缩

3.1 压缩在文件里的位置

ORC：每个 stream 按 256 KB 切块

一个 stream(比如 c 列的 DATA) ┌───┬──────────────┬───┬──────────────┬───┬──────┐ │头3│ 压缩块 1 │头3│ 压缩块 2 │头3│ 块 3 │ └───┴──────────────┴───┴──────────────┴───┴──────┘ 头 = (压缩后长度 << 1) | 是否原样存储 每块解压后最多 256 KB，块之间互不引用
  • 压缩块和行没有对应关系。行索引要记"块的偏移 + 块内偏移"。
  • 压缩后变大的块原样存储，读取时不用解压。

Parquet：每个 page 体整体压缩

一个 data page ┌──────────────┬──────────────────────────────┐ │ Page Header │ 压缩后的 page 体 │ │ (不压缩) │ = zstd(级别 + 值) │ └──────────────┴──────────────────────────────┘ Header 里记录压缩前后的大小 字典页也单独压缩
  • 一个 page 就是一段行，要读就整个 page 解压。
  • page 默认 1 MB 或 2 万行，压缩单位比 ORC 大，但每个 page 都单独压缩。
压缩单位小带来的影响 两种格式的压缩单位都只有几百 KB 到 1 MB，每块单独压缩。所以 zstd 的大窗口在这里发挥不出来，压缩级别从 1 提到 9，压缩率的提升比在大文件上小得多。另外，编码已经去掉了大部分冗余，通用压缩在列存上的压缩率比在普通文本上低。

3.2 压缩原理：LZ77 + 熵编码

所有常用的压缩算法都由这两种技术组合而成。

技术去掉什么冗余做法
LZ77重复出现的片段在最近的窗口(几十 KB 到几 MB)里找相同的片段。找到了就写一个 (往回多远 offset, 复制多长 length) 的引用，不再写原文。找不到的字节原样写出，叫 literal。
熵编码单个符号出现频率不均匀给常见的符号分配短码，少见的分配长码。Huffman 的码长必须是整数位；FSE / tANS 可以用小数位，更接近理论下限。

例子：abracadabra abracadabra(23 字节 = 184 位)

第一步 LZ77：从左往右扫，匹配至少 3 个字节才记引用。

a b r a c a d [往回7, 长4] 空格 [往回12, 长11] └ "abra" └ "abracadabra" 10 个 token。按固定位宽存(1 位标记 + 8 位)，共 90 位

第二步 Huffman：统计 token 里每个符号的频率。Deflate 的做法是把 literal 和匹配长度放进同一张符号表，offset 单独一张表。

符号abrcd空格长度 4长度 11offset 7offset 12
次数3111111111
码000100111001011101110111101
00 010 011 00 100 00 101 1110 0 110 1111 1 共 31 位 184 位(原文) → 90 位(只做 LZ77) → 31 位(LZ77 + Huffman，还不包括码表)

解压：查码表得到符号；遇到 literal 就输出它，遇到引用就从已经输出的内容里往回复制。不需要做任何搜索，所以 LZ 类算法的解压速度和压缩级别基本无关。

真实的实现里还要把码表写进每个块的开头，这在小数据块上占比很高。这也是压缩单位越小越难压缩的原因。

ORC

↓

↓

↓

Parquet

row group 统计：哪些 row group 能跳过
↓
字典过滤 + Bloom：查询值不在字典里就跳过
↓

↓

5. 相同点与不同点

5.1 相同点

  • 行列混合布局：先按行切成大块，块内按列存放，只读用到的列。
  • 元数据在尾部：写入时流式追加，读取时先读尾部。
  • 编码 + 通用压缩两层：字典、RLE、位打包之后再 zstd。
  • 多级统计和可选的 Bloom Filter，支持谓词下推。
  • 文件写完不能修改，更新和删除由 Paimon、Iceberg、Hive ACID 等上层实现。

5.2 不同点汇总

整数编码RLE v2，4 种子编码，每段 ≤ 512v1：字典或 PLAIN；RLE 段长度不限

6. 优势与劣势

ORC 的优势 ・索引更细且各列对齐，行组级 Bloom。
・RLE v2 对整数分布适应性强。
・高基数字符串也能用字典，存储更省。
・统计更全，有 sum、字符串总长度。
ORC 的劣势 ・字典不限大小：读取时堆里有大块长期存活的数据，GC 压力大。
・字典是否使用只按前 1 万行判断一次。
・生态较窄，类型扩展不灵活。
Parquet 的优势 ・生态最广，Spark、Iceberg、Arrow、DuckDB 都优先支持。
・字典最多 1 MB，读取时内存行为稳定。
・字典过滤，排序列的 RLE 段长度不限。
・嵌套数据友好，类型扩展灵活。
Parquet 的劣势 ・高基数字符串回退到 PLAIN，文件更大。
・page 索引各列不对齐，Bloom 粒度粗。
・每个 page 新建 zstd 解压流，堆外内存频繁申请释放。
・库的默认值保守(不压缩、v1 page)，要靠上层调整。
